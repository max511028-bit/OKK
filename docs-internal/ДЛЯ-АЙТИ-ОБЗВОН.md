# Голосовой бот-обзвонщик кандидатов — паспорт продукта для ИТ

> Версия: 2026-07-16. Подготовлено для передачи в ИТ-отдел (интеграция с
> Битрикс24 и корпоративной телефонией). Охватывает ТОЛЬКО продукт обзвона
> кандидатов. Контакт по вопросам: владелец продукта (Максим).

---

## 0. Что это (2 абзаца)

Автоматический обзвон базы кандидатов голосовым ботом. Рекрутёр загружает базу
(XLSX/ручной ввод) и выбирает сценарий разговора в веб-конструкторе → бот сам
звонит каждому кандидату, задаёт вопросы (актуальность поиска, возраст,
гражданство, стоп-факторы...), распознаёт ответы и классифицирует итог. На
выходе — живая воронка на веб-портале и Excel-отчёт: каждый контакт в одной из
категорий **ЦЕЛЕВОЙ** (100% годен) / **СПОРНЫЙ** (нужен взгляд рекрутёра) /
**НЕЦЕЛЕВОЙ** (недозвон, автоответчик, стоп-фактор), с записью разговора,
транскриптом и ответами.

Ключевая особенность: **все AI-компоненты работают локально** (распознавание
речи, синтез, LLM-анализ) — данные кандидатов не передаются во внешние
AI-сервисы. Боевой прогон: 129 контактов за 2ч46м в одну линию, конверсия
и качество классификации подтверждены аудитом.

## 1. Технологический стек

| Слой | Технологии |
|---|---|
| Backend (портал) | Python 3.10+, FastAPI + uvicorn, SQLite; nginx (reverse proxy, HTTPS) |
| Frontend | Одна страница vanilla JS (без сборки), REST к бэкенду |
| Голосовой агент | Python: pyVoIP 1.6.8 (SIP/RTP, кодек G.711 PCMA/PCMU; + 5 наших патчей стабильности), многопоточная пост-обработка |
| Распознавание речи (STT) | Vosk (offline): малая ru-модель для реального времени с грамматикой под вопрос + большая `vosk-model-ru-0.42` (~1.8 ГБ) для пере-распознавания записей |
| Синтез речи (TTS) | edge-tts (осн. голос) + Silero TTS (локальный сервер, 5 голосов); кэш фраз |
| LLM (анализ) | Ollama + qwen3 (0.6b/1.7b/8b), полностью локально. Роли: детекция роботов-автоответчиков, нормализация свободных ответов, пере-валидация ответов по записи, саммари для рекрутёра |
| Телефония (сейчас) | Novofon (экс-Zadarma): SIP-линия + Call API (JSON-RPC) + записи разговоров через их media API |
| CI/CD | GitHub Actions → rsync на VPS + рестарт systemd; 247 автотестов (pytest) |

## 2. Архитектура (текущая)

```
   Рекрутёр (браузер) ──HTTPS──► VPS (Ubuntu, nginx)
                                  ├─ FastAPI :8601 (кампании, воронка, отчёты)
                                  ├─ SQLite (контакты, попытки, ответы)
                                  └─ прокси к Novofon API (IP-whitelist)
                                        ▲ HTTP-поллинг (исходящий)
                                        │
   Машина агента (сейчас Windows-ПК) ───┘
   ├─ dispatch_agent.py — забирает контакты, звонит, шлёт результаты
   ├─ SIP/RTP (UDP) ◄──────► Novofon ◄──────► кандидат (PSTN/моб.)
   ├─ Vosk STT + Silero TTS + Ollama LLM (всё локально)
   └─ SSH reverse-туннель → VPS (доступ портала к LLM/TTS)
```

Принципы: машина агента **не требует входящих соединений** (работает за NAT,
только исходящие) — агент сам поллит портал. Портал — тонкий: хранение,
UI, отчёты; всё тяжёлое (звук, модели) — на машине агента.

## 3. ОТВЕТ на вопрос 1: «Нужно ли интегрировать в Б24? Какие сущности/логика/БП?»

**Встраивать сам сервис в Б24 не нужно** — он самодостаточен (свой UI,
БД, отчёты). Целесообразна интеграция **на уровне обмена данными** через
REST Б24. Рекомендуемая схема:

### Сущности
- **Кандидат** → лид Б24 (источник «Автообзвон») или элемент смарт-процесса
  «Кандидаты» — на ваш выбор, у нас жёсткой привязки нет.
- Поля, которые сервис отдаёт по каждому контакту (всё уже есть в REST):
  ФИО, телефон, **категория** (целевой/спорный/нецелевой) с обоснованием,
  исход звонка, вердикт, причина стопа, ответы на каждый вопрос сценария,
  длительность, число попыток, флаг «⚠ проверить» + комментарий автопроверки
  + LLM-саммари записи, ссылка на аудиозапись разговора.

### Логика/потоки
1. **Вход (Б24 → сервис):** выгрузка базы в кампанию. Вариант А — как сейчас,
   XLSX руками; вариант Б — по REST Б24 (`crm.lead.list`/smart-process items)
   автоматически создавать кампанию. Наш API загрузки уже принимает JSON.
2. **Выход (сервис → Б24):** по завершении обработки звонка — создание/
   обновление сущности через входящий вебхук Б24 (`crm.item.add/update`).
   Важно: у нас **двухфазный результат** (сразу после звонка + через ~1-2 мин
   уточнение по записи: категория может поменяться, напр. «спорный»→«робот») —
   поэтому обновление, а не только создание.
3. **БП в Б24 (предложение):**
   - ЦЕЛЕВОЙ → стадия «К связи с рекрутёром», задача на ответственного, SLA;
   - СПОРНЫЙ → стадия «Проверить», в комментарий — ⚠-причина + саммари + ссылка на запись;
   - НЕЦЕЛЕВОЙ → авто-закрытие с причиной (недозвон/робот/стоп-фактор).

### Оценка работ с нашей стороны
Исходящий коннектор в Б24 (вебхук, маппинг полей, ретраи) — **1–2 дня**.

### Встречные вопросы к вам
1. Какая сущность для кандидатов принята у вас (лиды / сделки / смарт-процессы / Bitrix24 HR)?
2. Облачный Б24 или коробка? (для коробки возможен прямой доступ к БД/шине)
3. Нужен ли обратный поток (изменения в Б24 → в сервис), или достаточно «сервис → Б24»?

## 4. ОТВЕТ на вопрос 2: «Какое окружение требуется?»

Два контура с разными требованиями:

### Контур А — портал (лёгкий)
| Параметр | Требование |
|---|---|
| ОС | Ubuntu 22.04+ (любой Linux) |
| Ресурсы | 1–2 vCPU, 1–2 ГБ RAM, 10 ГБ диск (сейчас живёт на 1 vCPU / 960 МБ) |
| ПО | nginx, Python 3.10+, systemd; БД — SQLite (файл; при желании мигрируется на Postgres) |
| Сеть | 443 наружу для пользователей; исходящий доступ к API телефонии |

### Контур Б — голосовой агент (тяжёлый)
| Параметр | Требование |
|---|---|
| ОС | Сейчас Windows 11; код кроссплатформенный Python — **перенос на Linux/Docker возможен** (Windows-специфика только в автозапуске и приоритете процесса, ~день работ) |
| CPU | 4+ ядра (реалтайм-распознавание во время разговора; наш пик — STT+TTS одновременно) |
| RAM | 8–16 ГБ (Vosk big ~1.8 ГБ + Ollama qwen3 2–6 ГБ + рабочие буферы) |
| GPU | Не обязателен (всё работает на CPU); с GPU LLM быстрее |
| Диск | ~15 ГБ под модели |
| Сеть | Только исходящие: SIP/RTP (UDP) к АТС/оператору, HTTPS к порталу. Входящих портов не требуется, NAT — ок |
| Масштаб | 1 агент = 1 параллельная линия (~50–80 сек/контакт). Больше линий = несколько экземпляров агента с разными SIP-учётками |

### Контур В — телефония (для интеграции с вашей корпоративной АТС)
Сервису нужно от АТС:
1. **SIP-учётка** (сервер/логин/пароль), кодек **G.711 (PCMA или PCMU)**, исходящие вызовы на мобильные;
2. Схема набора: сейчас используется callback-схема Novofon (API-запрос «соединить линию с номером») — при прямом SIP-транке вашей АТС станет проще (обычный исходящий INVITE, код это уже умеет);
3. **Записи разговоров**: сейчас забираем готовые записи по API Novofon (двухдорожечные WAV — на них построена пере-валидация ответов). Вопрос: ваша АТС пишет разговоры и отдаёт по API? Если нет — добавим запись на стороне агента (~1–2 дня);
4. Идентификатор звонка от АТС (для привязки записи к контакту).

**Встречные вопросы:** какая АТС (Asterisk/FreePBX, 3CX, Mango, UIS, МТС...)?
Есть ли SIP-транк для роботов? Ограничения по CPS/одновременным линиям?
Где хранятся записи и есть ли API к ним?

## 5. ОТВЕТ на вопрос 3: общее описание для админов (порты, данные, безопасность)

### Компоненты и порты
| Компонент | Где | Порт/протокол | Направление |
|---|---|---|---|
| nginx | VPS | 80/443 TCP | вход от пользователей |
| FastAPI (uvicorn) | VPS | 127.0.0.1:8601 | локально за nginx |
| Агент → портал | машина агента | HTTPS 443 | исходящее, поллинг ~20с |
| Агент → АТС | машина агента | SIP 5060/UDP + RTP (динамич. UDP) | исходящее |
| Ollama (LLM) | машина агента | 127.0.0.1:11434 | локально; наружу — через SSH-туннель к VPS |
| Silero TTS | машина агента | 127.0.0.1:5001 | локально; аналогично |
| SSH reverse-туннель | агент → VPS | 22 TCP исходящий | LLM/TTS для портала |

### Данные и ПДн
- Персональные данные кандидатов (ФИО, телефон, ответы) — в SQLite на VPS.
- Аудиозаписи — сейчас на стороне Novofon (ссылки в карточках).
- **STT/TTS/LLM — полностью локальные**: голос и данные не уходят в облачные AI-API.
- Оговорка для юристов: TTS edge-tts использует голосовой сервис Microsoft
  (текст фраз бота уходит в MS; ответы кандидатов — нет). Альтернатива уже
  встроена — локальный Silero (переключается настройкой сценария).

### Доступ и авторизация
- Портал: пароль → HMAC-токены (3 уровня: открытые read-эндпоинты, портальный
  пароль на действия, отдельный админ-пароль).
- Агент авторизуется на портале тем же механизмом; секреты — в env-файлах вне git.

### Эксплуатация
- Health-чеки: `/tasks/api/health`, `/tasks/api/ai/health`, heartbeat агента
  (индикатор на портале). Вотчдог на машине агента самовосстанавливает
  LLM/TTS/туннель (при входе + ежечасно).
- Логи: агент — файл на машине агента; бэкенд — journald.
- CI: GitHub Actions, деплой ~3–4 мин, smoke-тесты.
- Тесты: 247 (pytest), каждый боевой инцидент закрыт регресс-тестом.

## 6. Предугаданные вопросы (FAQ для ИТ)

**Лицензии компонентов?** FastAPI/pyVoIP/Ollama — MIT; Vosk — Apache 2.0;
qwen3 — Apache 2.0. ⚠ Два пункта на проверку юристами: edge-tts (неофициальный
клиент к сервису Microsoft) и модели Silero (лицензия ограничивает некоторые
коммерческие сценарии) — при сомнениях остаёмся полностью на Silero по
договорённости с их командой либо на альтернативном локальном TTS.

**Можно ли всё разместить в нашем контуре?** Да, полностью on-premise:
портал — любой Linux-хост, агент — Linux/Windows машина с моделями. Внешних
зависимостей, кроме телефонии, нет.

**Docker?** Портал — тривиально. Агент — возможен (звук идёт через UDP-сокеты,
не через аудиокарту), потребуется host-network для RTP.

**Как масштабировать на N параллельных линий?** N экземпляров агента с
отдельными SIP-учётками; портал уже раздаёт контакты атомарно (claim),
несколько агентов могут работать по одной кампании без конфликтов.

**Что с отказоустойчивостью?** Автоперезапуск агента при краше, авто-повтор
контактов при сбоях телефонии, недоставленные результаты сохраняются локально
и довозятся. Известный пробел: автоматических бэкапов SQLite пока нет
(в плане работ).

**Соответствие 152-ФЗ (локализация ПДн)?** Определяется размещением серверов —
при переносе в ваш контур вопрос закрывается автоматически. Запись разговора:
кандидат — вопрос уведомления о записи решается фразой в сценарии (правится
в конструкторе за минуту).

**Качество распознавания?** Двухступенчатое: реалтайм (малая модель с
грамматикой под вопрос) + пере-распознавание записи большой моделью с
LLM-сверкой ответов. Расхождения не перезаписываются молча — помечаются
«⚠ проверить» с саммари для рекрутёра.

**Что передаётся при хендовере?** Приватный GitHub-репозиторий (код + CI),
полная внутренняя документация `docs-internal/` (архитектура, API-справочник
на 116 эндпоинтов, схема БД, runbook эксплуатации, известный техдолг),
реестр доступов. Документация поддерживается в актуальном состоянии — это
требование зашито в процесс разработки.
