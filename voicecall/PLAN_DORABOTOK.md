# План доработок голосового бота (2026-07-03)

Самодостаточный план для выполнения. Контекст: голосовой бот обзвона
кандидатов. Портал https://portalsth.ru/voicecall/ (код `voicecall/index.html`,
бэкенд `tasks/api/main.py`), агент звонков на этом ПК (`voicecall/dispatch_agent.py`
→ `phone_call.py` → `dialog.py`/`stt.py`/`tts.py`/`call_api.py`).

## Как деплоить и проверять (ВАЖНО, прочитай до начала)

- **Деплой на портал**: `git push origin main` → GitHub Actions сам rsync-ает
  на VPS за 2-5 минут. После изменений в `tasks/api/main.py` нужно ещё
  перезапустить сервис: `ssh -i ~/.ssh/okk_key_openssh root@195.208.119.67
  "systemctl restart tasks-api.service"`.
- **Перезапуск локального агента** (после изменений в voicecall/*.py):
  PowerShell: `Stop-ScheduledTask -TaskName "STH-Dispatch-Agent"; Start-Sleep 2;
  Start-ScheduledTask -TaskName "STH-Dispatch-Agent"`.
- **Лог агента**: `C:\ProgramData\sth\dispatch-agent.log` (UTF-8! читать через
  `python -c "import io; print(''.join(io.open(r'C:\ProgramData\sth\dispatch-agent.log', encoding='utf-8', errors='replace').readlines()[-50:]))"`,
  НЕ через Get-Content — консоль cp1251 ломает кириллицу и падает на эмодзи).
- **Тесты бэкенда**: `cd OKK && python -m pytest tasks/api/tests/ -q
  --ignore=tasks/api/tests/test_ai_cache.py` (ai_cache флаки, игнорируем; сейчас 132 зелёных).
- **Синтаксис**: `python -m py_compile voicecall/<файл>.py` после каждой правки.
- Кодировка всех файлов — UTF-8. В .ps1 файлах кириллица требует BOM.

## Задача 1. Убрать 10-секундные паузы из-за LLM посреди разговора

**Проблема**: `dialog.py`, функция `llm_classify()` (~строка 225) ходит в
`https://portalsth.ru/tasks/api/validator/llm-classify` с `timeout=10`.
Когда Ollama недоступна/медленная, кандидат слушает тишину все 10 секунд
(реальные замеры в логах: «пауза перед фразой: 10836мс»). Вызывается это
посреди живого диалога — на второй непонятной попытке ответа.

**Что сделать** (в `voicecall/dialog.py`):
1. Снизить таймаут запроса с 10 до 2.5 секунд: `_urllib.urlopen(req, timeout=2.5)`.
2. Добавить модульный кэш-флаг доступности LLM:
   ```python
   _LLM_DEAD_UNTIL = 0.0  # time.time(), до которого LLM считаем недоступной
   ```
   В `llm_classify()`: если `time.time() < _LLM_DEAD_UNTIL` — сразу `return None`
   (не ходить в сеть). При любом исключении запроса — ставить
   `_LLM_DEAD_UNTIL = time.time() + 300` (5 минут не пробовать) и `return None`.
   Не забыть `import time` (проверить, он уже импортирован).
3. Поведение при недоступной LLM уже правильное (возврат None = «не распознано»,
   переспрос/пропуск) — менять не надо.

**Проверка**: `python -m py_compile voicecall/dialog.py`; юнит-проверка руками:
```python
import dialog, time
dialog._LLM_DEAD_UNTIL = time.time() + 300
assert dialog.llm_classify({"expect": "yesno", "bot": "?"}, "непонятно") is None  # мгновенно, без сети
```

## Задача 2. Убрать ~2.5-3с тишины перед первой фразой бота

**Проблема**: в `phone_call.py` перед началом диалога вызывается
`detect_voicemail(call)` — слушает линию до первой фразы бота
(`silence_before_speech_sec=2.0`, до 8с если что-то звучит). Кандидат
говорит «алло» и ~3 секунды ждёт ответа. Детекция автоответчика ПО ХОДУ
разговора уже есть (проверка `is_voicemail_phrase()` на каждой реплике +
свободный probe после 2 нераспознанных шагов + лимит 3 нераспознанных),
поэтому предварительная проверка больше не обязательна.

**Что сделать** (в `voicecall/phone_call.py`):
1. Найти ДВА места вызова `vm_text = detect_voicemail(call)` (одно в
   `run_call()`, второе в `run_call_via_bridge()`, ~строки 990 и 1130).
2. Удалить оба блока `log("Проверяю, не автоответчик ли это..."); vm_text =
   detect_voicemail(call); if vm_text: ...` ЦЕЛИКОМ (вместе с return).
   Строку `bridge_established_at = time.time()` над ними — ОСТАВИТЬ
   (используется для метрики «первая фраза»).
3. Функцию `detect_voicemail()` саму НЕ удалять (пусть остаётся, вдруг
   вернём) — только пометить в докстринге: «больше не вызывается перед
   диалогом, детекция идёт по ходу разговора (см. _run_dialog_loop)».
4. В `_run_dialog_loop` первая фраза бота говорится с
   `allow_interrupt=not first_phrase` — это остаётся как есть.

**Риск/компромисс (сознательный)**: чистый автоответчик теперь будет
ловиться не ДО первой фразы, а на 1-2-м шаге диалога (probe свободным
распознаванием). Чуть больше секунд эфира на автоответчиках, зато КАЖДЫЙ
живой кандидат получает мгновенное приветствие. Это осознанное решение,
не «забыли проверку».

**Проверка**: реальный тестовый звонок на свой номер: бот должен
поздороваться СРАЗУ после снятия трубки (в логе «первая фраза: <800мс»).
Звонок на номер с автоответчиком — должен завершиться status=voicemail
за первые 2 шага.

## Задача 4. Валидация сценария в конструкторе (слипшееся имя)

**Проблема**: в сценарии «Большой тест» тексты вида `{name}Здравствуйте!`
без разделителя — бот произносит «МаксимЗдравствуйте!». Код подстановки

**Что сделать**:
1. **Бэкенд** `tasks/api/main.py`: найти эндпоинты сохранения сценария
   `POST /voicecall/scripts` и `PUT /voicecall/scripts/{sid}` (~строка 5450+).
   Добавить функцию `_vcs_validate_steps(steps: list) -> list[str]`,
   возвращающую список ПРЕДУПРЕЖДЕНИЙ (не ошибок, сохранение не блокировать):
   - `{name}` сразу прилеплен к слову: regex `r"\{name\}[А-Яа-яЁёA-Za-z]"`
     или `r"[А-Яа-яЁёA-Za-z]\{name\}"` в любом текстовом поле шага
     (`bot`, `on_yes`, `on_no`, `on_no_follow`, `stop_msg`) →

   Ответ эндпоинтов дополнить полем `"warnings": [...]`.
2. **Фронтенд** `voicecall/index.html`: в конструкторе сценариев после
   сохранения, если в ответе есть непустой `warnings` — показать их

## Задача 7. Пере-валидация вердикта по записи звонка

**Цель**: страховка от ложных отказов из-за ошибок live-распознавания.
После звонка у нас есть перепроверенный транскрипт по WAV-записи
(точнее live). Если он противоречит live-вердикту — пометить контакт
«требует проверки человеком», НЕ менять вердикт автоматически.

**Как устроено сейчас** (что нужно знать):
- `voicecall/dispatch_agent.py`, `_recheck_transcript()` — фоновый поток,
  скачивает 2 WAV-дорожки звонка, распознаёт большой моделью, POST-ит
  склеенный текст `[Дорожка 1] ... [Дорожка 2] ...` на
  `POST /voicecall/dispatch/recheck-transcript`.
- Вердикты: `passed` (годен) / `stopped` (стоп-фактор, поле `stop_reason`
  вида «Судимости: да») / `declined`. Хранятся в `voicecall_contacts.verdict`
  и в `candidate_validations`.
- LLM доступна через `POST {portal}/ai/proxy/chat` (Ollama, модель
  `qwen3:1.7b`, см. пример вызова в `_normalize_free_answers()` там же).

**Что сделать**:
1. **Бэкенд** `tasks/api/main.py`: миграция — колонка
   `voicecall_contacts.needs_review INTEGER DEFAULT 0` (идиом `try:
   ALTER TABLE ... except sqlite3.OperationalError: pass` — примеры рядом
   в `init_db()`). Расширить `VCDispatchRecheckReq` полем
   `needs_review: Optional[bool] = None` и `review_reason: Optional[str] = None`;
   в обработчике — если пришло `needs_review=True`, ставить флаг контакту
   и дописывать `review_reason` в `candidate_validations.summary`.
2. **Агент** `dispatch_agent.py`, в `_recheck_transcript()` после получения
   транскриптов, ТОЛЬКО для звонков с вердиктом `stopped` (они самые
   рискованные — там мы отказали человеку):
   - взять `stop_reason` контакта (прокинуть его параметром из
     `_run_campaign` через `_fetch_and_attach_recording`, там уже
     передаётся result);
   - спросить LLM: «Бот отказал кандидату по причине: {stop_reason}.
     Вот полный транскрипт разговора по записи: {recheck}. Подтверждается
     ли причина отказа этим транскриптом? Ответь одним словом: да / нет /
     неясно»;
   - если ответ «нет» — слать `needs_review=True,
     review_reason="Запись не подтверждает причину отказа"`.
   - LLM недоступна/таймаут → просто ничего не делать (не блокировать).
3. **Фронтенд** `voicecall/index.html`: в списке контактов кампании у
   контакта с `needs_review=1` — бейдж «⚠ проверить» рядом со статусом;
   в карточке контакта — заметная строка с `review_reason`. Посмотреть
   `ctStatusPill()` и рендер таблицы контактов в `loadContacts()`.
4. **Тест**: POST recheck с `needs_review=true` → `GET /voicecall/
   contacts/{id}/detail` возвращает флаг.

## Задача 10. Недозвон — не дольше ~45 секунд

**Проблема**: сейчас недозвон может занимать до ~2 минут:
`incoming.get(timeout=70)` (ожидание, пока Novofon перезвонит на нашу
линию) + `wait_for_contact_talking(..., timeout=45)` (гудки кандидату).

**Что сделать** (в `voicecall/phone_call.py`, функция `run_call_via_bridge`):
1. `incoming.get(timeout=70)` → `timeout=30` (Novofon перезванивает за
   секунды; 30с — уже щедро; текст ошибки поправить на «за 30 сек»).
2. `wait_for_contact_talking(api_secret, call_session_id, timeout=45)` →
   `timeout=35` (35с ≈ 6-7 гудков; кто не взял за это время — не возьмёт).
   Комментарием указать: суммарный худший случай недозвона ≈ 45-50с.
3. НЕ трогать таймауты внутри самого диалога (max_total_sec и т.п.).

**Проверка**: реальный звонок на номер, где не берут трубку — от
«→ Звоню» до «← Итог: status=no_answer» в логе агента должно проходить
≤ ~50 секунд.
